# Gately 插件协议 v1（路线 B：外部插件）

插件是一个**独立运行的 HTTP 服务**，Gately 负责注册、监管（仅命令型）、健康检查
与页面反代，不把插件代码编译进 Gately。本文件是 v1 的完整约定。

发行层对齐 Magpie（registry + 一键安装 + 官方/社区源，见第 10 节）；
执行层 hooks 暂不做（理由见第 10 节）。

## 1. 两种插件形态

| 形态 | 谁运行服务 | Gately 做什么 | 适用场景 |
| --- | --- | --- | --- |
| `command` | Gately：按注册的绝对路径启动进程 | 分配回环端口、注入环境变量、捕获输出、健康检查、失败退避重启 | 插件与 Gately 同机部署，随 Gately 启停 |
| `url` | 你自己：Docker 容器、另一台主机、systemd 服务 | 只反代与健康检查，不管理进程 | 插件已有自己的部署方式（如容器） |

命令型插件必须监听 Gately 分配的端口：Gately 在启动时注入环境变量
`PLUGIN_PORT`（另有 `GATELY_PLUGIN_ID`、`GATELY_PLUGIN_NAME`）；注册时
`port` 填 0 表示自动分配，填固定值表示使用该端口（须保证不冲突）。

## 2. 注册字段

| 字段 | 说明 |
| --- | --- |
| `id` | 唯一标识：小写字母开头，仅小写字母、数字、`_`、`-`，≤32 字符；同时是反代路径的一部分 |
| `name` / `version` / `description` / `icon` | 展示用 |
| `kind` | `command` 或 `url` |
| `command` / `args` / `env` / `workDir` | 命令型：可执行文件**绝对路径**、参数、额外环境变量、工作目录 |
| `url` | URL 型：服务地址，如 `http://127.0.0.1:8080` |
| `port` | 命令型监听端口，0 为自动分配 |
| `healthPath` | 健康检查路径，默认留空表示只做 TCP 连通检查；填 `/health` 则要求 2 秒内返回 < 400 |
| `enabled` | 关闭后不启动、不反代 |
| `scopes` | 插件声明的、调用 Gately API 时需要的权限（见第 5 节） |

创建时 Gately 生成一个 32 字节共享密钥 `secret`，**仅在创建响应里返回一次**。
列表与详情接口不返回它；轮换办法是删除重建（后续版本再补轮换接口）。

## 3. 页面反代

- 插件页面地址：`/api/plugin/pages/<id>/`（不带斜杠访问会自动 301 到带斜杠版，
  以保证插件内相对链接与静态资源正确解析）。
- 反代剥离浏览器带来的 `Cookie` 与 `Authorization`，改注入以下头：
  - `X-Gately-Plugin`：插件 ID
  - `X-Gately-User`：当前登录用户名
  - `X-Gately-Role`：`admin` 或 `readonly`
  - `X-Gately-Plugin-Token`：创建时生成的共享密钥；插件**可选**校验它，
    以确认请求确实经 Gately 反代而来（不要把该密钥写进公开仓库）。
- 插件未运行返回 503，插件服务无响应返回 502。
- 反代走标准库 `httputil.ReverseProxy`，WebSocket 升级（101）随之透传。

## 4. 生命周期与健康检查

- Gately 启动时自动启动全部已启用的插件；插件模块关闭（设置里关掉插件中心）
  时不注册任何接口。
- 健康检查每 30 秒一次：命令型先看进程是否存活，再按 `healthPath` 检查；
  URL 型只做 HTTP/TCP 检查。
- 连续 3 次失败：URL 型标记为 `error`（不自动重启，因为进程不在 Gately 手里）；
  命令型按 5s / 10s / 20s / 40s / 60s 退避重启，5 次耗尽后标记 `error` 并停止
  自动拉起，需手动启动。
- 插件标准输出与标准错误逐行写入插件中心日志（管理界面 `/api/plugin/logs` 可见）。

## 5. 鉴权模型（复用 Gately 现有机制，不发明新令牌体系）

- **管理接口**（`GET /api/plugin/plugins` 等）走框架统一鉴权：
  登录会话按角色放行（只读账号仅 GET）；API 令牌按路径推导
  `plugin:read`（GET/HEAD）与 `plugin:write`（其他方法）。
- **插件页面**（iframe 打开）凭登录会话访问：只读账号可看页面，写操作仍受
  上述规则约束（页面内对 Gately API 的调用同样要过这一关）。
- **插件调 Gately API**：插件是普通 API 客户端。管理员在“API 令牌”页按插件
  声明的 `scopes` 创建令牌，插件以 `Authorization: Bearer <令牌>` 调用。
  v1 不在服务端强制“插件只能用它声明的 scopes”，声明只用于提示管理员授什么权。

## 6. 信任边界（v1 明确不解决的问题）

1. **命令插件与 Gately 同权**：以 Gately 进程的操作系统用户身份运行，
   能读写 Gately 能读写的一切。只安装完全信任的插件。
2. **插件页面与管理界面同源**：iframe 里的插件脚本可凭当前会话调用 Gately API。
   这与“只装可信插件”是同一条边界；独立插件源、沙箱 iframe、插件专属
   细粒度令牌属于后续版本，不在本版承诺。
3. **URL 型插件可指向内网任意地址**：注册本身是管理员写操作（`plugin:write`），
   与 Gately 其他模块可指向内网服务的能力同级，不新增越权面。
4. **无资源限制**：v1 不对插件做 CPU/内存/带宽配额；容器型插件请用容器自身限制。

## 7. 定制构建

插件中心是可选模块：build tag 为 `no_plugin`，`modules.json` 与
`internal/modules/registry` 的 Catalog 中均已登记；裁掉它时管理界面自动隐藏
入口与页面（走框架的 `absentModules` 机制）。

## 8. 最小示例

见 `examples/plugin-hello/`：一个纯标准库 Python 服务，监听 `PLUGIN_PORT`，
`/` 回显反代注入的头，`/health` 返回 ok。注册步骤：

1. 把 `hello.py` 放到服务器（如 `/usr/local/bin/plugin-hello.py`）并 `chmod +x`；
2. 管理界面 → 插件中心 → 添加插件：类型选“命令”，可执行文件填绝对路径，
   端口填 0，健康检查填 `/health`，启用；
3. 点“打开”，即见回显页；创建时返回的密钥可用于校验
   `X-Gately-Plugin-Token`（示例未校验，仅回显）。

## 9. v1 不做

- 执行层 hooks（流量拦截，见第 10 节的决策）；
- 插件间通信、事件总线、插件调用插件；
- 动态侧栏入口：插件页目前从插件中心“打开”进入（路由 `/plugin/<id>`），
  侧栏动态条目待后续版本；
- 插件配置的可视化表单生成（插件自己的页面里做）；
- 多语言管理文案：本版仅中英，其他语言回退英语。

## 10. 发行层（对齐 Magpie，2026-11-04 决策）

### 10.0 决策：对齐发行层，不对齐执行层

- Magpie 的核心业务就是 LLM 请求路径，进程内 hooks（onRequest/onResponse）
  是它的自然扩展点；Gately 的核心是网络 plumbing，热路径必须快且 fail-safe，
  进程外逐请求调 hooks 会给每个被代请求加延迟与故障点，且与现有
  WAF / 访问控制 / ForwardAuth 重叠。
- 触发“对齐 Magpie”的实际问题是官方/第三方区分与一键安装，发行层完整回答了它。
- 下一个插件（导航页）需要的是页面 + 发行，不需要 hooks。
- hooks 不是砍掉，是延后：清单预留 `capabilities` 字段，未来有真实拦截需求时
  再加 `hooks` 能力，发行设计不阻碍它。

### 10.1 清单 plugin.json

插件包（目录或 zip）根部放 `plugin.json`，字段与第 2 节注册字段对应，另加：

- `entry`：命令型为包内相对可执行路径（安装后解析为绝对路径）；URL 型不填。
- `options`：默认选项对象（JSON），安装后管理员可改。
- `capabilities`：能力声明数组，本版只有 `pages`（提供页面）；预留 `hooks`（未来）。
- `minGatelyVersion`：可选，声明最低 Gately 版本。

### 10.2 Registry 索引

Registry 就是一份 JSON 索引，可由 HTTP(S) URL 或本地目录提供：

```json
{ "name": "...", "plugins": [ { "id": "...", "downloadUrl": "...", "…清单字段" } ] }
```

- 来源分两类：官方源（Gately 项目维护的索引；地址待官方插件发布时确定，
  本版先以空源占位）与社区源（管理员自行添加的 URL 或本地目录）。
- 管理界面按来源打标：官方 / 社区——这就是官方插件与第三方插件的区分，
  同一条安装路径，不设白名单以外的特权。
- 信任边界：registry 本身须可信，恶意 registry 可投递恶意插件；本版不做
  签名校验（后续加固项），只装可信源。

### 10.3 安装 / 升级 / 卸载

- 安装来源三条：registry（一键）、本地目录（含 plugin.json）、上传 zip 包。
- registry 安装面向命令型插件（自包含包）；URL 型插件仍手动注册，
  它的部署在 Gately 之外。
- 安装动作：下载（或复制）包到插件目录 → 解压 → 按清单注册（命令型 entry
  解析为绝对路径）→ 写入 options 默认值 → 启用。
- 升级：registry 里有更新版本时，管理界面显示“可升级”，升级即按同一清单重装
  （旧进程先停）。
- 卸载：停进程、删注册；下载文件是否删除由管理员勾选。
- 版本检查只在管理界面打开 / 手动刷新时做，不设后台定时检查。

### 10.4 选项 options

- 选项存在插件配置里，管理界面以 JSON 文本编辑（可视化表单生成仍是后续版本）。
- 命令型插件：Gately 启动时把选项 JSON 注入环境变量 `PLUGIN_OPTIONS`
  （与 Magpie 的 ctx.options 对应，进程外版）。
- URL 型插件：选项只作记录，不投递——它的配置随它自己的部署走（compose/env），
  这是本版的明确局限。

### 10.5 实现说明（发行层已落地）

- 本地目录源 = 内含 `index.json` 的目录；registry 安装包必须是 zip
  （本地目录安装才接受 plain 目录包）。
- registry 安装只面向命令型插件；本地目录与上传安装同样只接受命令型清单
  （URL 型插件仍手动注册）。
- 安装目录为配置目录下的 `plugins/<id>/`；本地目录安装是复制，源目录原样保留。
- 升级保留密钥与启用状态，选项只补新清单带来的默认值（管理员改过的值不覆盖）；
  升级前先停旧进程。
- 选项编辑后，运行中的命令型插件重启一次以注入新 `PLUGIN_OPTIONS`；
  URL 型插件不重启（选项只作记录）。
- `minGatelyVersion` 在当前版本无法解析（如 dev 构建）时不拦截。
- 解压防 Zip-Slip、拒绝符号链接；安装包上限 64 MB、解压后上限 256 MB。
- 本版不做签名校验（见 10.2 信任边界），只装可信源。
